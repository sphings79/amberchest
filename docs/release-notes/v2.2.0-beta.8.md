**An eighth beta of 2.2.0.** It is not the newest stable release and it does not
move `latest`: the container image is
`ghcr.io/sphings79/amberchest:2.2.0-beta.8`. Please do not run it on an archive
you cannot afford to have a problem with.

This one is for hosts that cut a backup off, after #9, where Gmail closes the
connection with "Account exceeded command or bandwidth limits" during a big
first backup.

What it needs from you, if you have such a mailbox: a backup of it that used to
fail, and what the account and the log show now.

Report what you find in the issue or at
https://github.com/sphings79/amberchest/issues.

---

## A run the server ends is paused, not failed

When the server closes the connection in the middle of a run, or names a limit,
the run is **paused**: the account shows a yellow "Paused" and the reason, not a
red "Failed", and what was downloaded is kept. The next run carries on from
there. A wrong password or an unreachable server is still a failure.

You get one notification at the first pause of a row, not one per attempt.

## The schedule waits after a pause

Trying again an hour later may only keep the host closed. After a pause,
scheduled runs skip that account for 6 hours, then 12, 24 and at most 48 if it
keeps happening, and the log says until when. A run you start by hand is never
held back, and a run that gets through starts the count afresh.

## Most data per run

New in the account's Advanced settings: **Most data per run (MB)**. A run ends
cleanly, as a normal finished run, once it has downloaded that much, and the
rest follows in the next run. It is off by default (0): AmberChest has no number
for any host, so set it a little below the point where yours cuts you off.

## The scan in blocks

Reading what is in a folder was one command for the whole folder, so one with
tens of thousands of messages was a single big request, and the "pause between
fetches" of the account did not apply to it. It is now done in blocks of 1,000
UIDs with that pause between them.

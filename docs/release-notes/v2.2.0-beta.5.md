**A fifth beta of 2.2.0.** It is not the newest stable release and it does not
move `latest`: the container image is
`ghcr.io/sphings79/amberchest:2.2.0-beta.5`. Please do not run it on an archive
you cannot afford to have a problem with.

This one is about removing archived mail from the server (#3). It makes the
removal say why it leaves a message alone, and it no longer takes the server's
word that a deletion worked. Everything else is as in beta 4, which also
contains the read-only login, selecting several messages and the changes to
throwing messages out of the archive.

What it needs from you, if you use the removal: run it again on a folder where
some messages were left alone, and tell me what the log says (see below).

Report what you find in the issue or at
https://github.com/sphings79/amberchest/issues.

---

## The removal tells you why a message was left alone

A removal checks every message before it deletes it, and leaves alone what it
cannot prove. Until now you only saw the totals. The log now has one line per
folder with the number for each reason:

> INBOX: 9995 removed, 600 left alone (archived copy not intact 0, no checksum
> 600, not the archived message 0, not on the server 0, still on the server
> after deleting 0)

It is a warning when anything was left alone, so it shows at the default log
level. For the single messages, set `AMBERCHEST_LOG_LEVEL=debug` (the Home
Assistant add-on has the option `log_level`) and run the removal again: every
message that was left alone gets a line with its UID, its file and the reason.
The debug level is not the default because a folder with hundreds of such
messages would fill the log.

## A deletion is checked afterwards

A server can accept a deletion and still keep the message, as some providers do
with a trash folder. The removal used to count such a message as removed. It
now asks the server again for the messages it just deleted. Those the server
still lists are not counted as removed, are not marked, and show up in the
result as "still listed by the server after deleting", so the next backup keeps
them as before.

If the server cannot be asked, the deletion is taken as it was acknowledged,
and the log says so.

A second login that can only read, and a login that is harder to guess and
easier on your logs. Read the section on what changes for you before you
update a container that other programs talk to.

## A read-only login

Set `AMBERCHEST_UI_PASSWORD_READONLY` next to `AMBERCHEST_UI_PASSWORD` and the
interface has two logins. The new one sees every mailbox and can browse,
search, read, and download `.eml` files, PDFs, attachments and export files.
It cannot change settings or accounts, run a backup, a restore or a check,
discard messages, lock the archive, or see the log.

It is meant for somebody who should be able to find a mail, not run the
archive: a partner, an accountant, a second person in the house. There is no
per-mailbox permission; the read-only login sees all of them.

What a read-only login may do is an allowlist in the server. A route added
later is closed to it until someone opens it on purpose. The settings are not
sent to it at all, which keeps the MCP token and the addresses of the
integrations away from it.

It needs `AMBERCHEST_UI_PASSWORD` and has to differ from it, otherwise it is
ignored and the log says so. The Home Assistant add-on gets the option
`ui_password_readonly` with the add-on release that follows this one.

## A login that is harder to guess

- **Wrong passwords are slowed down.** Five wrong tries lock that client
  address out for 15 minutes, twice as long every time it comes back and does
  it again, up to a day. A ceiling across all addresses slows down guessing
  that is spread over many of them. The master password prompt is limited the
  same way. Every wrong try and every lockout is in the log.
- **Logins expire.** An administrator login lasts 12 hours, the read-only one
  seven days. The desktop app's own token lasts as long as the app runs.
- **The password comparison no longer shows how much of it matched**, or how
  long it is.

### Behind a reverse proxy

A lockout goes by the client address, and behind a proxy that address comes
from `X-Forwarded-For`. That header is only believed when the request arrives
from a loopback or private address, which is where a proxy next to the
container normally is: Traefik, nginx or Caddy on the same host or the same
Docker network. A client that reaches the port directly is judged by its own
address, which it cannot forge.

Before this release the header was believed from anyone. If your proxy has a
public address, list it in `AMBERCHEST_TRUSTED_PROXIES` (comma separated
addresses or CIDR ranges, a number of hops, or `none`). Otherwise all visitors
look the same to the server, and one person guessing wrong can lock everybody
out. If the log shows the same address for every failed login, that is what
happened.

## No token in an address

The session token used to go into the address of every download link and of
the live event stream, where it ended up in server logs, proxy logs and the
browser history. It now only travels in a header. A download link and the
event stream use a one-time ticket instead: good for one request to one path,
and worthless after a minute.

The desktop window receives its token in the part of the address after `#`,
which is never sent to a server.

## Smaller things

- Responses carry `X-Content-Type-Options`, `Referrer-Policy: no-referrer` and
  `X-Frame-Options: SAMEORIGIN`, and the API says `Cache-Control: no-store`.
  The frame header is left out in the Home Assistant add-on, and by
  `AMBERCHEST_ALLOW_FRAMING=true` for a dashboard that embeds the interface.
- A viewer that signs out leaves the archive unlocked for everybody else; the
  button for it says "Sign out" instead of "Lock".
- A new account that signs in with OAuth can be saved without a password. The
  Save button used to stay disabled until one was typed in, although an OAuth
  account has none (#8, also fixed in 2.1.2).
- The server package has tests of its own now, and the web package has tests
  for how a credential reaches the server.

## What changes for you

- **`?token=` in an address no longer works.** A script that passed the token
  in the query string has to send `Authorization: Bearer <token>`. The Home
  Assistant integration already does.
- **A login is no longer valid for ever.** A program that logs in once and
  keeps the token has to log in again after 12 hours, which is what the Home
  Assistant integration does when it is told no.
- **Five wrong passwords lock an address.** A program with a wrong password
  that keeps trying - the Home Assistant integration polls every 30 seconds -
  locks its own address for 15 minutes. Fix the password, wait, or restart.
- **A proxy with a public address needs `AMBERCHEST_TRUSTED_PROXIES`**, see
  above.
- **Embedding the interface in another site's frame is off.** Set
  `AMBERCHEST_ALLOW_FRAMING=true` to turn it back on.

## Update the desktop app and the containers together

The desktop app can operate a container somewhere else. A desktop app of this
release reaching an older container falls back to the token in the address
for downloads and live progress, because the older server knows no tickets.
An older desktop app reaching a container of this release cannot: downloads
are refused and the live progress does not arrive. Update both.

## Not in this release

A read-only login still sees the absolute paths of the files on the server,
and every login sees everybody's export bundles. There is no content security
policy yet; the interface renders HTML mail and that needs a careful pass.

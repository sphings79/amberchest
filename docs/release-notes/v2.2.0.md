A second login that can only read, selecting and throwing out many messages
at once, removing archived mail from the server, and a login that is harder to
guess and easier on your logs. Read the section on what changes for you before
you update a container that other programs talk to, and the section on removal
before you switch that on: it deletes on your mail server.

## A read-only login

Set `AMBERCHEST_UI_PASSWORD_READONLY` next to `AMBERCHEST_UI_PASSWORD` and the
interface has two logins. The new one sees every mailbox and can browse,
search, read, and download `.eml` files, PDFs, attachments and export files.
It cannot change settings or accounts, run a backup, a restore or a check,
discard messages, lock the archive, or see the log.

It is meant for somebody who should be able to find a mail, not run the
archive: a partner, an accountant, a second person in the house. There is no
per-mailbox permission; the read-only login sees all of them.

What a read-only login may do is an allowlist in the server. A route added
later is closed to it until someone opens it on purpose. The settings are not
sent to it at all, which keeps the MCP token and the addresses of the
integrations away from it.

It needs `AMBERCHEST_UI_PASSWORD` and has to differ from it, otherwise it is
ignored and the log says so. The Home Assistant add-on gets the option
`ui_password_readonly` with the add-on release that follows this one.

## Select several messages

The mailbox, the search results and the list of discarded messages have a
checkbox on every row. Shift-click takes everything between two rows.

A bar above the list shows how many are selected and what can be done with
them. Select the whole page and it offers **all N matches** of the current
search or filter, beyond what has been loaded: search for a sender, select
all, and throw out every newsletter from them in one go.

- **Throw out of the archive** removes the files and the index entries, the
  same as the right click menu on a single message. Nothing on the server is
  touched, and the archive remembers the decision so the next backup does not
  fetch the mail again. A confirmation names the number first.
- **Take back**, in "Discarded", works on a selection or on everything a
  filter finds. The mails come home with the next backup.

A search is worked off in batches of 500, so a hundred thousand matches show
progress, can be stopped, and do not run into a timeout. What was done stays
done if you stop. The read-only login gets neither the checkboxes nor the calls
behind them.

## Throwing a message out removes every copy of it

A mail that is stored once and shown in several folders, as Gmail does it, is
one file with several places. Throwing it out of one folder used to leave the
file with the others.

Now all of its places go, by default, and each one keeps its own record that
the mail was thrown out on purpose. The records have to be per folder: the
backup looks at every folder, and one without a record would fetch the mail
again from there. The file is deleted once.

- On a single message the right click menu always takes all places and tells
  you how many copies in other folders went with it.
- The dialog of the selection action has a switch, **"Also the copies in other
  folders"**, on by default. Off, only the copy in the chosen folder goes, and
  the file stays as long as another folder shows it.
- An index rebuilt from the files keeps the record of every folder.

A mail that was deleted on the server is kept in the `_deleted` folder of the
account. Throwing such a message out marked it as thrown out but left its file
behind, and so did discarding a whole folder. Both now delete the file. This
has been so since the right click menu was added in 2.1.0. If you used it on
mail from the `_deleted` filter, "Check archive" lists the files that stayed as
files that no index entry points at, and they are safe to delete.

## Remove archived mail from the server

Some hosts only let you delete thirty messages at a time, and a mailbox of a
hundred thousand never gets smaller. With **"Allow removing archived mail from
the server"** switched on in an account's settings - it is off by default - the
account card gets a **"Remove from the server ..."** button.

**This deletes mail on your mail server for good.** Try it first on a folder
where a mistake does not hurt, and keep a second copy of the archive while you
do.

The dialog shows what it would take - messages and size per folder - before it
does anything. You can leave folders out, and take only mail older than a
number of days. Nothing starts until you have typed the name of the account.

### What has to be true before a message is deleted

Each one is checked right before it goes, not from an earlier look:

- the archived file is there, can be read (and decrypted), and still matches
  the checksum taken when it was downloaded. A message without a checksum is
  left alone; "Check archive" adds one;
- the folder still has the UIDVALIDITY the stored UIDs belong to;
- the message under that UID on the server is the one that was archived.

Anything else is left alone and counted in the result, with the reason. The log
has a line per folder with the number for each reason, and for the first
messages in a folder that are not the archived ones it says which details
differ; with
`AMBERCHEST_LOG_LEVEL=debug` (the add-on option `log_level`) every message that
was left alone gets a line of its own.

It sets `\Deleted` and sends `UID EXPUNGE` for exactly those UIDs, in batches
of 500 with a pause in between. A server without UIDPLUS is refused: it would
expunge every flagged message in the folder, including ones this never looked
at. Afterwards it asks the server again for what it deleted. A message the
server still lists - some providers keep what is put in a trash folder - is not
counted as removed, and the result says so.

### What the next backup does

The archive keeps its copy. The messages are marked as deleted from the server
on purpose, in the index and in each folder's journal, so the next backup does
not take them for a deletion made elsewhere - whatever the policy for mail that
is deleted on the server says. That includes "mirror", which would otherwise
delete the only copy left. An index rebuilt from the files keeps the marks. A
message that turns up on the server again, for instance after a restore, is an
ordinary message once more.

### Good to know

- **Gmail:** deleting in a label folder only removes that label. The mail
  stays in "All Mail", so the server does not get smaller from it.
- The MCP interface cannot do this. A read-only login cannot do it either.
- "Restore" can write the messages back to a server later.

## A login that is harder to guess

- **Wrong passwords are slowed down.** Five wrong tries lock that client
  address out for 15 minutes, twice as long every time it comes back and does
  it again, up to a day. A ceiling across all addresses slows down guessing
  that is spread over many of them. The master password prompt is limited the
  same way. Every wrong try and every lockout is in the log.
- **Logins expire.** An administrator login lasts 12 hours, the read-only one
  seven days. The desktop app's own token lasts as long as the app runs.
- **The password comparison no longer shows how much of it matched**, or how
  long it is.

### Behind a reverse proxy

A lockout goes by the client address, and behind a proxy that address comes
from `X-Forwarded-For`. That header is only believed when the request arrives
from a loopback or private address, which is where a proxy next to the
container normally is: Traefik, nginx or Caddy on the same host or the same
Docker network. A client that reaches the port directly is judged by its own
address, which it cannot forge.

Before this release the header was believed from anyone. If your proxy has a
public address, list it in `AMBERCHEST_TRUSTED_PROXIES` (comma separated
addresses or CIDR ranges, a number of hops, or `none`). Otherwise all visitors
look the same to the server, and one person guessing wrong can lock everybody
out. If the log shows the same address for every failed login, that is what
happened.

## No token in an address

The session token used to go into the address of every download link and of
the live event stream, where it ended up in server logs, proxy logs and the
browser history. It now only travels in a header. A download link and the
event stream use a one-time ticket instead: good for one request to one path,
and worthless after a minute.

The desktop window receives its token in the part of the address after `#`,
which is never sent to a server.

## Smaller things

- Responses carry `X-Content-Type-Options`, `Referrer-Policy: no-referrer` and
  `X-Frame-Options: SAMEORIGIN`, and the API says `Cache-Control: no-store`.
  The frame header is left out in the Home Assistant add-on, and by
  `AMBERCHEST_ALLOW_FRAMING=true` for a dashboard that embeds the interface.
- A viewer that signs out leaves the archive unlocked for everybody else; the
  button for it says "Sign out" instead of "Lock".
- **Log level and log file.** The detail level of the log is a setting now
  (Settings -> Log) and applies at once, also in the desktop app. A log file
  can be written as well: up to three files of 50 MB, with a download button on
  the log page.
- A new account that signs in with OAuth can be saved without a password. The
  Save button used to stay disabled until one was typed in, although an OAuth
  account has none (#8, also fixed in 2.1.2).
- The server package has tests of its own now, and the web package has tests
  for how a credential reaches the server.

## What changes for you

- **`?token=` in an address no longer works.** A script that passed the token
  in the query string has to send `Authorization: Bearer <token>`. The Home
  Assistant integration already does.
- **A login is no longer valid for ever.** A program that logs in once and
  keeps the token has to log in again after 12 hours, which is what the Home
  Assistant integration does when it is told no.
- **Five wrong passwords lock an address.** A program with a wrong password
  that keeps trying - the Home Assistant integration polls every 30 seconds -
  locks its own address for 15 minutes. Fix the password, wait, or restart.
- **A proxy with a public address needs `AMBERCHEST_TRUSTED_PROXIES`**, see
  above.
- **Embedding the interface in another site's frame is off.** Set
  `AMBERCHEST_ALLOW_FRAMING=true` to turn it back on.

## Update the desktop app and the containers together

The desktop app can operate a container somewhere else. A desktop app of this
release reaching an older container falls back to the token in the address
for downloads and live progress, because the older server knows no tickets.
An older desktop app reaching a container of this release cannot: downloads
are refused and the live progress does not arrive. Update both.

## Not in this release

A read-only login still sees the absolute paths of the files on the server,
and every login sees everybody's export bundles. There is no content security
policy yet; the interface renders HTML mail and that needs a careful pass.
